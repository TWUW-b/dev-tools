# 文面の書き方

読み手はアプリの利用者とクライアント。開発の言葉を知らない前提で書く。

## 1 変更 = 1 項目

| フィールド | 書き方 | 例 |
|---|---|---|
| `category` | 3 つだけ。増やさない | `fix` 直したこと / `improve` 使いやすくしたこと / `feature` 新しくできること |
| `headline` | 「〜しました」で終える 1 文 | 編集画面で保存ボタンが押せないことがあるのを直しました |
| `where` | 画面上の場所。メニューの名前を `>` でつなぐ | 案件 > 編集 |
| `before` | これまでの困りごと。1〜2 文 | 担当者を変えたあと、保存ボタンが灰色のまま押せないことがありました。 |
| `after` | これからどうなるか。結果を 1〜2 文 | 担当者を変えると、すぐに保存できます。 |
| `feedback_id` | 元になったフィードバックの番号（任意）。画面には出ない | 24 |

- `before` と `after` は必ず対で書く。片方だけだと何が変わったか伝わらない。
- 原因や直し方（「キャッシュを消すようにした」など）は書かない。利用者に見える結果だけを書く。

## 書いてはいけないもの

`check-release-note.mjs` が error にする。

- ファイル名、API のパス、列名や enum などの snake_case の識別子
- チケット ID（`ABC-123`）、issue / PR 番号（`#45`）
- TODO / FIXME

画面の文言をそのまま引くときは、画面に出ている日本語を使う（`status=draft` ではなく「下書き」）。

## 号

| フィールド | 書き方 |
|---|---|
| `version` | 第N号。前号の番号に 1 を足す（管理 API の一覧で前号を確かめる） |
| `title` | その号でいちばん大きな変更を 1 文で |
| `summary` | 号全体のまとめ。2〜3 文まで |
| `released_on` | 利用者がその変更を使えるようになる日（YYYY-MM-DD） |

前号は API が公開日から自動で選ぶので、原稿には書かない。

## 載せないもの

- 利用者から見えない変更（内部の整理、テストの追加など）
- まだ本番に出ていない変更。ローカルや dev の号と本番の号は別物で、デプロイしても移らない
